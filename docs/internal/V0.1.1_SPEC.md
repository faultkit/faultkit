# FaultKit v0.1.1 — Productization Spec

**What this is:** a deployment & go-to-market fine-tune. Successor to the
archived `V0.1_SPEC.md` (product/feature spec, now under
`.archive/docs-internal-pre-redesign-2026-09-07/`). Baseline before this pass is
the git tag `pre-redesign-baseline` (`v0.1.2-40-g38a68ba`).

**The guardrail for this whole document:** the injection engine, the scenario
set, and the provider set do **not** change here, and every rule in `CLAUDE.md`
stays in force. This spec fine-tunes *how faultkit is packaged, entered,
released, documented, and demoed* — plus **one additive feature that
productization requires: a machine-readable `report/v1` with a verdict, so a
coding agent can consume a run's result** (§2b). Any *other* code feature
change is out of scope — see §8.

OTEL / telemetry / trace correlation is out of scope (the only telemetry stance
that stays: faultkit never phones home).

---

## 1. What this spec does NOT change

Locked, carried forward exactly as they are today:

- **Feature set** — the 14 shipped scenarios, the failure-mode × provider
  fixture model, the Bedrock provider, all provider fixtures.
- **Technical approach** — proxy (martian MITM), eBPF, LD_PRELOAD shim;
  single-shot; no daemon; no TUI.
- **Contracts** — exit-code constants, YAML scenario schema, CLI command and
  flag names. These are user promises; unchanged.
- **Rules** — OSS/Pro boundary, no new dependencies without approval,
  supply-chain pinning, error-handling and testing conventions, no telemetry.

A change to any of the above is a *feature* change and belongs in a separate
feature spec, not here.

## 2. The changes — skill-first entry + an agent-readable report

Two additive changes. Neither touches the injection engine, the scenarios, or
the providers.

### 2a. Entry point becomes skill-first

Today the primary user learns the binary and runs it by hand. The fine-tune:
the **primary entry point is a skill**, and the skill drives the **existing**
binary — it wraps, it does not replace.

- One skill, three modes: `/faultkit:review`, `/faultkit:harden`,
  `/faultkit:prove`. All three call today's `faultkit` CLI with today's
  scenarios and flags.
- `faultcheck` skill is retired; its content becomes the core of
  `/faultkit:review`, rewritten invariant-first.

### 2b. Report v1 — the feature that makes faultkit agent-consumable

A coding agent needs a structured result, not prose it must scrape. faultkit
already has the plumbing: `internal/report.Summary` + `WriteJSON()`, emitted to
a file via `--report <path>`. This change **versions that report and adds a
verdict block** — it is not a new subsystem.

- **Schema field.** `Summary` gains `"schema": "faultkit.dev/report/v1"`. The
  schema is versioned; a change to it is a breaking change.
- **Verdict block.** A `verdict` object — `{ "state": ..., "reason": ... }` —
  computed from the *same* source as the exit code (today: `run.go`'s dispatch
  over `FiredCount()` and target exit). The exit-code contract is **unchanged**;
  the verdict just makes the proof state legible in the JSON. The two can never
  disagree because they are derived together:

  | `verdict.state` | condition | exit code (unchanged) |
  |---|---|---|
  | `invalid_evidence` | `faults_fired == 0` | `ExitFaultNotFired` |
  | `silent_failure_confirmed` | fault fired, target exit ≠ 0 | `ExitTargetFailed` |
  | `invariant_proven_under_fault` | fault fired, target exit 0 | `ExitOK` |

- **stdout to the agent.** Add `--json` to write the report to **stdout** (the
  human summary goes to stderr, as it already does). `--report <path>` keeps
  writing to a file. An agent runs `faultkit run --json ... -- <cmd>` and parses
  stdout.
- **Blocks in v1:** `schema`, `scenario`, `injected` (events + fired count),
  `target` (command, exit_code, duration), `verdict`. All but `schema` and
  `verdict` already exist on `Summary`.
- **Deferred (follow-up, not v1):** `target.stdout_tail` / `stderr_tail`. The
  runner streams the target's stdout/stderr live and does not capture them
  (`runner.go`); a tail buffer is a separate small change. v1 carries the exit
  code, which the verdict needs; the tails are a debugging nicety on top.

## 3. Packaging & distribution

All existing channels; nothing new to build:

- **Skill repo:** `github.com/faultkit/skills` (marketplace), plugin `faultkit`.
  One marketplace, room for more skills later. The `faultkit/ai-resilience`
  split idea is dropped.
- **Binary:** the channels already live — Homebrew tap, AUR (`faultkit-bin`),
  `go install`, `install.sh`. The skill installs the binary via one of these;
  it does not bundle a second copy.
- **Install flow:** `/plugin marketplace add faultkit/skills` →
  `/plugin install faultkit@faultkit` → skill ensures the binary is present.

---

## 4. Release & GTM strategy

Feature-neutral sequencing — these are packaging/marketing milestones, not new
code:

- **v0.1.1 — productization pass:** skill-first entry, the `report/v1` +
  verdict feature (§2b), proof-oriented README + docs, one flagship demo
  (double-charge), skill repo published. `report/v1` is the *only* feature that
  ships in this pass; nothing else.
- **Adoption:** 3 design partners run the existing faultkit via the skill in
  their CI; depth over breadth.
- **GitHub Action** (`faultkit/action@v1`): packaging of the existing CLI as a
  CI step + a PR comment carrying the proof state. This is distribution, not a
  new capability.
- **Show HN** once the flagship demo + skill + docs are coherent.

Any scenario additions or new output formats are *feature* work; this spec
sequences the productization around whatever feature set exists, it does not
schedule features.

## 5. Docs — reframe, don't re-feature

- **README:** proof-oriented framing of the *existing* capabilities — "prove
  your agent fails safe under a real dependency fault", not a feature list.
- **`docs/agents.md`** (new doc, no new code): how a coding agent / the skill
  drives faultkit using today's CLI and exit codes. This is the doc the skill
  reads.
- `scenarios.md`, `yaml-schema.md`, `quickstart.md`, `ci.md` stay; their
  "roadmap / what's coming" sections point at this spec.

## 7. Metrics — without phone-home

No telemetry. Public signals only:

|---|---|

| Design-partner proofs | Manual, 3 partners |

| Time-to-first-proof | Stopwatch with design partners |

## 8. Explicitly out of scope for this spec

Deferred to a separate *feature* spec if ever wanted — **not** started here,
current behavior preserved:

| Deferred item | Disposition |
|---|---|
| Shrinking the scenario set (14 → 5) | Keep all 14 |
| Agent-first CLI *beyond* `report/v1` + `--json` — auto-JSON on non-TTY, `scenarios --json`, `explain`, `init --agent`, `seed` | Separate feature spec; not this pass (only the explicit `--json` + `report/v1` of §2b ship) |
| `target.stdout_tail` / `stderr_tail` capture | Follow-up; needs a runner tail buffer (§2b) |
| Pulling back Bedrock / narrowing providers | Keep |
| OTEL / traceparent / OTLP export | Out of scope (see header) |

2. **CLAUDE.md touch-ups:** naming consistency only (e.g. `faultkit-dev` →

## 10. One sentence

If this pass lands, a developer types `/faultkit:prove` in their coding agent,
and the **existing** faultkit engine proves in CI that their agent fails safe
under a real dependency fault — same scenarios, same providers, now with a
`report/v1` the agent can read and a skill-shaped front door.
